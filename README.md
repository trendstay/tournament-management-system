# Сервис организации спортивных турниров

## О системе

Приложение автоматизирует работу компании, которая организует спортивные
турниры: ведёт справочник видов спорта, регистрирует пользователей
(администраторов, менеджеров, игроков, капитанов, тренеров и судей),
формирует команды, проводит турниры, назначает судей и учитывает результаты
матчей.

Проект создан как Spring Boot-приложение со сборкой Maven. Данные на этом
этапе хранятся в памяти в потокобезопасных коллекциях; структура классов
подготовлена для последующего перехода к реляционной базе данных.

## Технологии

- Java 17;
- Spring Boot 4 (Spring MVC);
- Maven (Maven Wrapper приложен к проекту);
- JUnit 5 (Jupiter);
- `java.util.logging` для журналирования.

## Структура проекта

| Пакет | Назначение |
|-------|------------|
| `com.tournament.model` | Доменная модель: сущности и их бизнес-правила. |
| `com.tournament.model.enums` | Перечисления: роль пользователя, вид спорта, статус матча. |
| `com.tournament.model.user` | Иерархия пользователей: базовый класс и роли. |
| `com.tournament.model.team` | Команда, её тренер, капитан и состав игроков. |
| `com.tournament.model.tournament` | Турнир, его судья, участники и турнирная таблица. |
| `com.tournament.model.match` | Матч, счёт, победитель и протокол. |
| `com.tournament.repository` | Интерфейсы хранения и in-memory реализации. |
| `com.tournament.service` | Бизнес-логика: пользователи, команды, турниры, матчи. |
| `com.tournament.util` | Вспомогательные классы (именованные потоки). |

### Пользователи и роли

`User` — абстрактный базовый класс: хранит идентификатор, email, хэш пароля,
имя, фамилию, телефон и роль. Он задаёт общий контракт полномочий, который
реализуют наследники:

| Класс | Роль | Создание турнира | Управление пользователями | Управление командой | Судейство |
|-------|------|:---:|:---:|:---:|:---:|
| `Admin` | `ADMIN` | да | да | да | нет |
| `Manager` | `MANAGER` | да | нет | да | нет |
| `Player` | `PLAYER` | нет | нет | нет | нет |
| `Captain` | `CAPTAIN` | нет | нет | да | нет |
| `Coach` | `COACH` | нет | нет | да | нет |
| `Referee` | `REFEREE` | нет | нет | нет | да |

`Captain` наследуется от `Player`: капитан всегда является игроком команды,
но дополнительно может управлять её составом.

### Команда

`Team` хранит название (бизнес-ключ), город, тренера (`Coach`), капитана
(`Captain`) и список игроков (`List<Player>`). Методы `addPlayer`,
`removePlayerByEmail`, `findPlayerByEmail`, `findPlayerByFullName` реализуют
добавление, поиск и удаление элементов коллекции. Назначение капитана
автоматически добавляет его в состав команды.

### Турнир

`Tournament` относится к виду спорта (`SportType`), имеет даты начала и
окончания, призовой фонд, главного судью (`Referee`) и множество команд
(`Set<Team>`). Множество не позволяет зарегистрировать одну и ту же команду
дважды. Метод `isRegistrationOpen()` проверяет окно регистрации, а
`generateStandingsTable()` формирует текстовую турнирную таблицу.

### Матч

`Match` связывает две команды, турнир и судью, хранит дату, счёт и статус.
Методы `updateScore`, `getHomeGoals`, `getAwayGoals`, `getWinner`, `isDraw`
и `generateMatchReport` реализуют валидацию, разбор строки счёта,
определение победителя и вывод протокола.

## Соответствие ER-модели (лабораторная работа № 2)

| Сущность ER-модели | Реализация в коде |
|--------------------|-------------------|
| Пользователь | `User` и наследники `Admin`, `Manager`, `Player`, `Captain`, `Coach`, `Referee` |
| Вид спорта | перечисление `SportType` (название, описание, допустимость ничьей) |
| Команда | `Team` |
| Турнир | `Tournament` |
| Матч | `Match` |
| Связь «Вид спорта 1:M Турнир» | `Tournament#getSportType()` |
| Связь «Турнир M:N Команда» | `Tournament#getTeams()` |
| Связь «Турнир 1:M Матч» | `Match#getTournament()` |
| Связь «Пользователь-судья 1:M Матч» | `Match#getReferee()` |
| Связь «Команда 1:M Игрок» | `Team#getPlayers()` |

Дополнительно, по замечаниям преподавателя, явно выделены сущности
«Игрок» (`Player`), «Тренер» (`Coach`) и «Судья» (`Referee`), а также роль
`CAPTAIN`. Класс `CustomerUser` удалён: покупателей в предметной области нет.

## Коллекции и алгоритмы

- `List<Player>` — состав команды: добавление, поиск по email и ФИО, удаление;
- `Set<Team>` — участники турнира: защита от повторной регистрации;
- `Map<Long, T>` (`ConcurrentHashMap`) — хранение сущностей в репозиториях;
- циклы, условия, форматирование строк — турнирная таблица и протокол матча;
- поиск по полям реализован в репозиториях: по email, роли, фамилии, городу,
  названию турнира, виду спорта, статусу матча, турниру и судье.

## Многопоточность

`MatchService#processMatchesConcurrently` обрабатывает коллекцию матчей в пуле
из именованных потоков `match-worker-1`, `match-worker-2`, `match-worker-3`.
Потоки синхронизируются на старте, поэтому в логе видно, что работу реально
выполняют разные потоки. Метод возвращает `MatchProcessingReport` с
количеством обработанных матчей, именами потоков и затраченным временем.

## Сборка и запуск

```bash
./mvnw clean verify        # компиляция, тесты, проверка сборки
./mvnw spring-boot:run     # запуск демонстрационного сценария
```

Демонстрация в `TournamentServiceApplication` регистрирует пользователей всех
ролей, создаёт две команды с тренерами, капитанами и игроками, проводит
турнир, завершает матч и запускает многопоточную обработку коллекции матчей.

## Тесты

Unit-тесты написаны на JUnit 5 и покрывают:

- регистрацию пользователей всех ролей, валидацию email и пароля,
  уникальность email, поиск и удаление;
- состав команды, назначение тренера и капитана, поиск игроков;
- регистрацию команд на турнир, окно регистрации, судью, турнирную таблицу;
- счёт, определение победителя, ничью и протокол матча;
- многопоточную обработку коллекции и имена потоков;
- in-memory репозитории: назначение идентификаторов, поиск, удаление.

## CI

### GitHub Actions

Файл `.github/workflows/maven.yml` запускает `./mvnw clean verify` на каждый
push и pull request, а также вручную (`workflow_dispatch`). Дополнительно
выполняется проверка `scripts/check-no-var.sh`, запрещающая использование
`var`. Отчёты Surefire сохраняются в артефактах сборки.

### GitLab CI

Файл `.gitlab-ci.yml` содержит обязательный блок `default.tags` с тегом
`k8s-internal` — без него job не находит раннер и пайплайн остаётся в
состоянии backoff. Пайплайн выполняет `check-no-var.sh` и
`mvn clean verify`, а отчёты JUnit передаёт в GitLab через `artifacts.reports.junit`.

## Соглашения проекта

- `var` не используется — только конкретные типы;
- каждый класс отвечает за одну задачу (SRP);
- хранение описано интерфейсами `BaseRepository` и `*Repository`, общая
  реализация вынесена в абстрактный `AbstractInMemoryRepository`;
- бизнес-логика разделена по сервисам: пользователи, команды, турниры, матчи;
- лабораторные работы ведутся в отдельных ветках, pull request не закрывается
  до получения Approve.
